# How a merge reaches console.thriveiii.com

Written because nothing in the repository said. `dist/thrive-console.html` is gitignored, so the
path from a merge to the served file is not obvious, and a phase that is "merged" is not
finished until it is served.

## The mechanism, with evidence

**GitHub Pages, deploying from a branch. There is no workflow file, and that is not an
omission.**

Evidence, gathered from the Actions API rather than assumed:

| Question | Answer | How it was established |
|---|---|---|
| Is there a workflow file? | No. `.github/` does not exist in the repository. | `find .github -type f` returns nothing |
| What runs on a push? | A workflow named `pages build and deployment`, path `dynamic/pages/pages-build-deployment`, event `dynamic` | 53 runs listed through the Actions API |
| Which branch triggers it? | `main`, on all 30 of the runs that carry a head branch | run list, grouped by `head_branch` |
| Is it automatic? | Yes. The most recent run started within minutes of the phase 1 merge | run timestamps against the merge time |

A path beginning `dynamic/` and an event of `dynamic` is GitHub's own builder rather than
anything in this repository. That is what "Deploy from a branch" produces: GitHub builds the
branch as a static site and no YAML exists to read.

Two files in the repository root confirm the same shape from the other direction. `.nojekyll`
is empty and exists only to stop Jekyll processing, which matters because `library/` would
otherwise be left alone but any future `_`-prefixed directory would be silently dropped.
`CNAME` contains `console.thriveiii.com`, which is how Pages knows the custom domain.

## What is actually served, and what is not

**This is the part worth reading twice.**

- **Served:** everything committed on `main`. That includes `library/console.html`, which is
  generated by `tools/bundle.js` and **is committed on purpose**, plus `library/*.js`,
  `library/*.css`, `assets/`, `opp/`, and the redirect at `index.html`.
- **Never served:** `dist/thrive-console.html`. `.gitignore` contains `dist/`, so it is never
  committed and Pages never sees it. It is the offline single file, built locally on demand.

So "confirmed present in the served file" means `library/console.html` and the scripts it
links, not `dist/`. A change that only appears in `dist/` has not shipped.

**The one manual step.** `tools/bundle.js` is run by a person, not by CI. If somebody edits
`library/app.js` or any `library/*.html` view and does not run it, `library/console.html` goes
stale and the served shell keeps the old markup while the linked scripts change underneath it.
Gate 10 catches exactly this by rebuilding and comparing, which is why it exists.

## To confirm a merge reached the site

For someone who has never done it:

1. Merge the pull request into `main`.
2. Open the repository's Actions tab. A run named `pages build and deployment` starts within
   about a minute. Wait for it to finish.
3. Open `https://console.thriveiii.com/library/console.html` and hard reload, because Pages sets
   long cache headers and a normal reload can serve the previous copy.
4. Search the source for the version marker of the phase that was merged.

## What could not be verified from here

The sandbox this console is developed in routes outbound HTTPS through a proxy that refuses
`console.thriveiii.com`: `curl` returns `CONNECT tunnel failed, response 403`. So the served
file could not be fetched and compared against a local build from this environment, and the
comparison WO-012 §2.3 asks for is recorded as not performed rather than described as if it
had been.

Everything above about the mechanism comes from the Actions API and from the repository, both
of which are reachable. The one thing missing is the byte comparison, and step 4 above is how a
person performs it in a browser in under a minute.
