# Cloudflare Pages — the migration runbook (execution of HOSTING_MIGRATION_PLAN)

**Decision (approved):** move the console off Netlify onto **Cloudflare Pages**, as a drop-in — the
same `node tools/bundle.js` build, the same `publish/` output, the same `_headers`, `pagePublish_`
**unchanged**, `console.thriveiii.com` kept. Object-storage page publishing stays a *later* escalation,
only if we ever exceed Cloudflare's 500 builds/month free ceiling.

**What this PR does and does not do.** This PR adds the in-repo Cloudflare config (`.node-version`,
`wrangler.toml`) and this runbook. It changes **nothing** about the build, the relay, `pagePublish_`,
or `netlify.toml` (kept for instant rollback). **No DNS change is made by the author** — the DNS cutover
is Thyab's hand-step, below. Nothing here touches the live site until Thyab does step 2b.

---

## 1. What Cloudflare Pages serves, and why nothing breaks

Cloudflare Pages runs the **same build we give Netlify** and serves the **same tree**:

| Setting | Value | Source of truth |
|---|---|---|
| Build command | `node tools/bundle.js` | Cloudflare dashboard (step 2a) |
| Build output directory | `publish` | `wrangler.toml` (`pages_build_output_dir`) + dashboard |
| Node version | `20.11.1` | `.node-version` (build needs ≥ 16.7 for `fs.cpSync`, `tools/bundle.js`) |
| No npm install | there is no `package.json`; the build is pure Node stdlib | — |

- **`_headers` is honored.** Cloudflare Pages reads a `_headers` file at the **root of the build
  output** — exactly where our build writes it (`publish/_headers`, generated by `tools/bundle.js`).
  It uses the same syntax Netlify does, so the no-stale-HTML guarantee is preserved unchanged:
  `/library/board.html` → `Cache-Control: public, no-cache, must-revalidate`; `/*` →
  `public, max-age=0, must-revalidate`. (This is the one thing plain GitHub Pages could not do, and
  the reason we chose Cloudflare Pages over Pages.)
- **The integrity probe, `version.json`, and the build marker still work unchanged** — they are all
  host-independent (established in `HOSTING_MIGRATION_PLAN.md`, STEP 1c): the root "Test board file"
  probe fetches `./version.json` and `./library/board.html` by **relative** path and SHA-256-compares
  to `boardSha256`; `version.json` is written by the same build; the `<meta name="thrive-build">`
  marker is in the HTML. None of them reference the host, so they behave identically on Cloudflare.
- **`pagePublish_` is untouched.** It commits `opp/<slug>/index.html` to the **repo** (not to a host);
  Cloudflare Pages, connected to the same repo, rebuilds on that commit and serves the new page. No
  relay change, no `pagePublish_` change.
- **`opp/<slug>` clean URLs work.** Cloudflare Pages serves `opp/<slug>/index.html` for the
  no-trailing-slash link form `console.thriveiii.com/opp/<slug>` (`liveUrl()`,
  `tools/board-send.src.js:33`), the same directory-index behavior Netlify gives. (Cloudflare may
  308-redirect `/opp/<slug>` → `/opp/<slug>/`; browsers follow it. This is called out in the live
  checklist to confirm.)

## 2. The exact hand-steps for Thyab (numbered, platform-labeled)

> Do these in order. Nothing is irreversible until 2b, and 2b is reversible in minutes (section 4).

### 2a. Cloudflare dashboard — create the Pages project (no DNS yet)

1. **[Cloudflare dashboard]** Sign in at `dash.cloudflare.com`. In the left sidebar choose
   **Workers & Pages → Create → Pages → Connect to Git**.
2. **[Cloudflare dashboard]** Authorize the GitHub app for the `thriveiii` org and select the
   **`thriveiii/thrive-console`** repository. Production branch: **`main`**.
3. **[Cloudflare dashboard]** Build settings:
   - **Framework preset:** `None`.
   - **Build command:** `node tools/bundle.js`
   - **Build output directory:** `publish`
   - (Node version is taken from `.node-version` = `20.11.1`; no env var needed. If you ever want to
     set it explicitly, add a build variable `NODE_VERSION = 20.11.1`.)
4. **[Cloudflare dashboard]** **Save and Deploy.** Cloudflare runs `node tools/bundle.js` and
   publishes `publish/`. When it finishes, it gives a temporary URL like
   `https://thrive-console.pages.dev`.
5. **[browser]** Open `https://thrive-console.pages.dev` and run the **live verification checklist
   (section 3) against the `pages.dev` URL first** — before any DNS change. The board should load,
   an existing `/opp/<slug>` should serve, and the integrity probe should pass. Netlify is still live
   and untouched at this point.

### 2b. DNS — point `console.thriveiii.com` at Cloudflare Pages (the cutover)

> This is the only step that changes what visitors get. Do it only after 2a's checklist passes on
> `pages.dev`.

1. **[Cloudflare dashboard → your Pages project → Custom domains]** Click **Set up a custom domain**,
   enter **`console.thriveiii.com`**, and follow the prompt. Cloudflare will tell you the target to
   point at (a `CNAME` to **`thrive-console.pages.dev`**) and will auto-provision the TLS certificate.
2. **[your DNS provider for `thriveiii.com`]** Change the DNS record for the **`console`** host:
   - **From:** the existing record that points `console` at **Netlify** (today this is a `CNAME` to
     your Netlify site, e.g. `…netlify.app`, or an `A`/`ALIAS` to a Netlify load-balancer address).
   - **To:** a **`CNAME`** record: name **`console`**, target **`thrive-console.pages.dev`**.
   - If `thriveiii.com`'s DNS is *already managed inside Cloudflare* (nameservers on Cloudflare), the
     Custom-domains step in 2b.1 creates this record for you automatically — you do not edit DNS by
     hand; just confirm the record appears as a proxied `CNAME` to `thrive-console.pages.dev`.
   - **Change only the `console` subdomain record.** Do not touch the apex `thriveiii.com`, the mail
     (`MX`), or `hi@`/`SPF`/`DKIM` records — email (`FROM_EMAIL_L5 = hi@thriveiii.com`) is unrelated
     to this host.
3. **[browser]** Wait for propagation (usually minutes; DNS TTL dependent) and for Cloudflare to show
   the certificate as **Active**, then run the **full live verification checklist (section 3)** against
   `https://console.thriveiii.com`.

### 2c. Keep Netlify as instant rollback (do NOT delete anything yet)

1. **[do nothing destructive]** Leave the Netlify site **connected and enabled** through the
   verification window. `netlify.toml` stays in the repo (this PR does not remove it). Because both
   hosts build the identical `publish/` tree, Netlify remains a ready, byte-identical fallback.
2. **[Netlify dashboard — optional, after cutover]** You may **pause auto-publishing** on the Netlify
   site (Site configuration → Build & deploy → Stop builds) so commits stop spending Netlify credits,
   while keeping the site able to serve if you revert DNS. Do **not** delete the Netlify site until
   section 4's "when to delete" is satisfied.

## 3. Live verification checklist (behavior, not just the build marker)

Run against `thrive-console.pages.dev` first (2a.5), then against `console.thriveiii.com` after cutover
(2b.3). Every item is a real user behavior.

1. **Shell serves.** `https://console.thriveiii.com/` redirects into the board and
   `https://console.thriveiii.com/library/board.html` loads; sign in and the board renders with lanes.
2. **Existing page still serves.** Open `https://console.thriveiii.com/opp/<an existing slug>` (pick one
   from the board). It renders the published page (a 308 to add a trailing slash is fine; the page must
   ultimately load).
3. **A NEW page publish goes live without Netlify.** From the console, publish a page (New message →
   upload a page, or promote a Library template) so the relay commits `opp/<new-slug>/index.html` to the
   repo. Confirm: the Cloudflare **Pages** project shows a new build from that commit; then
   `https://console.thriveiii.com/opp/<new-slug>` resolves and the board's own verify-live settles the
   card to live. (Confirm the **Netlify** deploy log shows this did **not** require Netlify — Netlify may
   also build if still enabled, but the live page is served by Cloudflare.)
4. **`_headers` no-stale works.** In the browser devtools Network tab, reload
   `console.thriveiii.com/library/board.html` and confirm the response header
   `Cache-Control: public, no-cache, must-revalidate`; confirm any other path under `/*` shows
   `max-age=0, must-revalidate`. Then push a trivial shell change, rebuild, and confirm a hard-reload
   serves the **new** build (no old shell stuck in cache). The root "Test board file" probe passes
   (bytes + SHA-256 match `version.json`).
5. **Core flows work live** (on `console.thriveiii.com`, signed in):
   - **Card tap → control room:** tapping a card opens the opportunity window on Details; the four
     gates (Message / Page / Contact / Activity) work.
   - **Send:** the Message gate's Send button sends (a `console_mail` row is written; per-recipient
     status shows); B2 suppression and the live-page send gate still apply.
   - **Contacts:** the Contacts surface lists contacts; opening one shows their templates + full
     conversation; a reply tag opens the conversation.
   - **New message (three paths):** New message shows the three options (text only / upload a page or
     campaign / pick from Library) and each opens its editor.
6. **Mobile smoke (optional but recommended):** on a phone, the board swipes and the control-room Send
   is reachable (mobile-first is already shipped; just confirm it survived the host move — it will, the
   bytes are identical).

If every item passes on `console.thriveiii.com`, the migration is verified.

## 4. Rollback, and when to delete `netlify.toml`

### The single revert

**One DNS change restores Netlify.** In your DNS provider, point the **`console`** record back to
**Netlify** (the exact value it had before 2b.2 — the `…netlify.app` CNAME or the Netlify
load-balancer `A`/`ALIAS`). Because Netlify builds the identical `publish/` tree, it serves the same
bytes; nothing in the repo or the relay changed, so there is nothing else to undo. Re-enable Netlify
auto-publishing if you paused it in 2c.2. Propagation is DNS-TTL fast.

There is no code rollback: this PR adds only config files and docs. If you want to also drop the
Cloudflare config, delete `.node-version` and `wrangler.toml` — they are inert without a Cloudflare
Pages project pointed at the repo.

### When to delete `netlify.toml` (a LATER follow-up PR, not this one)

Delete `netlify.toml` (and, if desired, delete the Netlify site) **only after** all of the following
hold, and as a **separate follow-up PR**:

1. `console.thriveiii.com` has served from Cloudflare Pages for a full verification window (recommend
   at least a few days of normal use, including at least one real page publish that went live via
   Cloudflare per checklist item 3).
2. The `_headers` no-stale behavior is confirmed on Cloudflare (checklist item 4).
3. You are confident you will not need the instant DNS rollback.

Until then, `netlify.toml` stays so the rollback in this section remains a pure DNS flip. When you do
remove it, that follow-up PR should also update `docs/DEPLOY.md` (currently describes the dormant
GitHub-Pages setup) to describe Cloudflare Pages as the live host.
